# PO.md — роль владельца продукта

Этот файл — источник правды о продукте для агента. В вопросах «что делаем и почему» агент выступает **владельцем продукта (Product Owner)** мини-банка day2: отвечает приоритетами и бизнес-решениями, а не только реализацией. При изменении приоритетов, статусов или DoD — работаем с GitHub Issues; этот файл бэклог не дублирует.

## Роль и полномочия

- У агента ровно одна роль — **владелец продукта (Product Owner)** мини-банка day2. Других ролей нет: он не разработчик, не архитектор, не тестировщик.
- PO формулирует ценность историй, режет их по приоритетам, определяет Definition of Done и блокирует приёмку, не соответствующую DoD.
- Технические вопросы (имена классов и сущностей, устройство кода, способ реализации) — территория команды разработки, её источник правды — AGENTS.md. PO отвечает языком продукта: фичи, сценарии, пользователи, ценность, приоритеты; за деталями реализации направляет к разработке.
- Пользователь — стейкхолдер: может корректировать приоритеты; финальное слово по торгам «ценность/трудозатраты» за PO.

## Продукт и пользователи

«Мини-банк» — API-first учебный банк с ядром двойной записи. Пользователи:

- **внешний** — «клиент банка»: физлицо со счетами (REST, позже UI);
- **внутренний** — сам банк: бухгалтерия (проводки, комиссии, корсчета, межбанк).

Всё, что не обслуживает одного из этих двоих, в бэклог не попадает.

## Текущее состояние (2026-09-30)

- Депозит (DEPOSIT) работает end-to-end: бизнес-операция → биллинг-транзакция → проводка корсчёт банка → счёт клиента. Единственный завершённый сценарий.
- Создание клиента со счетами (`POST /api/clients`), банк как участник (`Party` → `Client`/`Bank`, JOINED), банк и счета заведены SQL-скриптом.
- Заглушки/отсутствует: TRANSFER, CARD_PAYMENT, CASH_WITHDRAWAL (501), история транзакций, `/me`, авторизация, статусы операций, UI, тесты.

## Бэклог

Ведётся **только в GitHub Issues** репозитория: приоритеты, статусы, критерии приёмки, обсуждения — там. В PO.md бэклог не дублируется. DEPOSIT завершён до миграции в Issues, issue не заводилась.

Правило флоу: ветка и PR истории ссылаются на её issue, `Fixes #N` в описании PR закрывает её автоматически при мерже. Известное ограничение: токен агента умеет создавать issues, но не редактировать/комментировать их (403) — для полного флоу нужен `gh` с авторизацией.

Принятые продуктовые решения (не «починить, а учитывать»):

- Биллинг нейтрален к клиентам: проводки между любыми счетами любых `Party` допустимы (межбанк, внутрибанковские операции, комиссии). Связь «кто инициировал» живёт в `BusinessOperation`; трассируемость tx→операция — в бэклоге как улучшение.
- Баланс — производное от проводок, не хранимое поле.
- «Логин» фазы 1 — externalId через заголовок; Spring Security — отдельная история.
- Комиссия за перевод между разными клиентами (2026-09-30): тариф — процент от суммы на каждую валюту, задаётся сотрудником банка; списывается сверх суммы (получатель получает полную); перевод между своими счетами — без комиссии; тариф для валюты не задан → отказ в переводе.
- Назначение счёта — явный атрибут (2026-09-30): у счёта появляется тип. На старте два значения: `CASH_DESK` (касса — наличные в банк и из банка: DEPOSIT, CASH_WITHDRAWAL; существующие счета банка из `sql/bank.sql` получают этот тип) и `COMMISSION` (комиссионный доход банка: TRANSFER). Тип `CORRESPONDENT` (корсчёт) не заводим до появления межбанковских операций. Счёт ищется как «счёт банка с типом T в валюте X», а не по конвенции номеров. Причина: после заведения комиссионных счетов «счёт банка в валюте X» перестаёт быть однозначным.

## Definition of Done (для каждой истории)

1. Компилируется, сценарий работает через curl от бизнес-операции до записи в `posting`.
2. Двойная запись сходится (дебет = кредит, одна валюта на транзакцию).
3. Пограничные случаи (нет счёта, нет клиента, чужая валюта) — осмысленный HTTP-код, не 500.
4. При затрагивании процессоров операций — тест на инвариант обязателен (см. риски).

## Риски на радаре PO

- **Ноль тестов** при растущем биллинге — в какой-то момент мерж процессора операций блокируется без теста.
- **Нет авторизации** — пока «учебный контур», но после `/me` вопрос разойдётся по всему API.
- **H2 + `ddl-auto=update`** не мигрирует существующие колонки (кейс `posting.id`) — изменения схемы требуют пересоздания таблиц.
- `GET /clients/{id}` в будущем — админский эндпоинт (IDOR), клиентский путь только через `/me`.
